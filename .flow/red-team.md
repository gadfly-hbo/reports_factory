## Top Kill-Assumptions（排序：影响 × 可能性 × 测试成本）

### KA-1｜根因诊断可能不完整
- **Claim（钢人版）**：用户「完全不是我想要的」= 职责三层倒置；把推进权交给 AI 就能命中预期。钢人：诊断有扎实证据——审计确认人承担全部流程推进、AI 仅 5 个零散按钮，与 AGENTS.md 蓝图语义直接冲突。
- **Fails if**：用户试用时不满的其实是内容质量、模板观感或某具体交互细节，编排改造后体感依旧「不是想要的」——诊断对了原则层、错了个案根因。
- **Evidence to get this week**：向用户拿到试用时的 2–3 个具体「不对劲」瞬间（哪个页面、点了什么、期望什么）；对照本次诊断逐条归因。
- **Kill criterion**：若具体不满全部落在输出质量/视觉层而与推进方式无关 → 改造方向降级为「质量修复优先，编排改造缓行」。
- **Cheapest test**：一次 10 分钟用户回访（问题清单见 PRD 风险节），零代码。

### KA-2｜AI 草案质量 × 推进自动化 = 审批负担可能不降反升
- **Claim（钢人版）**：五个 AI 用点已有 zod + 白名单 + 确定性兜底，质量有程序保障；AI 先行产草案比人从零填表快。
- **Fails if**：自动推进批量产出的蓝图/推荐草案质量平庸，人仍要逐关口细审甚至返工——偏离信号②从「人做流程引擎」变成「人做垃圾分拣员」，总决策力消耗更高。
- **Evidence to get this week**：用现有 2–3 个真实项目跑一轮五用点，人以「可直接批准 / 小改 / 重来」三档盲评草案质量。
- **Kill criterion**：可直接批准率 < 50% → 先修草案质量再谈推进自动化，或编排器默认停在更细的关口粒度。
- **Cheapest test**：半天人肉评审（复用现有 UI，零新代码）。

### KA-3｜成本封顶对默认供应商链无效（已有反证）
- **Claim（钢人版）**：成本已有计量（outboundLog 聚合），补一个阈值判断即成预算门。
- **Fails if**：默认链含小米 token-plan，其 `usage.cost` 如实记 0（AGENT-RUNTIME §10 已知坑）——按成本封顶对它完全不生效，预算门形同虚设，P4 合规是纸面的。
- **Evidence to get this week**：查 outboundLog 中 xiaomi provider 的 cost 字段实际值（预期全 0）。
- **Kill criterion**：不 kill 方案，kill「按成本单线封顶」的设计——预算门必须按 **调用次数 + 轮次 + 墙钟** 三线封顶，成本线仅作次级参考；此项为 PRD 硬约束。
- **Cheapest test**：一条 SQL/grep 查历史日志。

### KA-4｜关口设计可能两头不讨好
- **Claim（钢人版）**：编排器「推进到下一关口停下」，关口呈现差异 + 批准/驳回，决策点清晰。
- **Fails if**：关口切得太细（每阶段多次确认）→ 没解决人肉瓶颈；切得太粗（一键跑到导出）→ 关键决策被稀释、G1/提案应用/导出确认被包裹绕过。
- **Evidence to get this week**：从 PRD 输出关口清单，逐个对照「这是决策还是例行确认」；例行确认必须由程序放行，只有取舍判断留给人。
- **Kill criterion**：不 kill；若关口清单中例行确认 > 一半 → 重新切分（GRILL 阶段自证）。
- **Cheapest test**：纸面关口表 + 对照现有 4 个人工决策点。

### KA-5｜模型单发可靠性长循环未验（低风险）
- **Claim（钢人版）**：工人模式下每阶段仍是独立单发 completion，不涉及长 tool-call 循环，可靠性风险与现状持平。
- **Fails if**：编排器实际需要跨阶段多轮调用串联，落入 §8 未验证区（mimo 仅 4 轮验证）。
- **Evidence**：确认编排器每个阶段仍是独立单发（架构约束写入 PRD）。
- **Kill criterion**：若设计上必须引入多轮 tool-call 循环 → 触发 §8 闸门，方案回炉。
- **Cheapest test**：PRD 架构节自查。

## What's Well-Reasoned（不制造怀疑）

- **工人模式的选择有标准背书**：§5 矩阵「流程能画出 → 工人模式」是确定性结论，不引入 tool-call 循环规避 §8 闸门，是本提案最稳的一步。
- **围栏资产盘点扎实**：审计逐文件确认白名单/批准门/schema/兜底均有程序背书，「不许动」清单具体可执行，复用改造风险低。
- **诊断有代码级证据**：偏离信号② 的认定基于 workbench/UI 实际接线，不是观感。
- **回放基建可复用**：recording.ts 已存在，P6 验证路径成本低。

## What I Couldn't Assess

- 用户试用的具体场景与失败瞬间（KA-1 的证据缺口，IMPLEMENT 前须补）。
- 现有五个 AI 用点在真实项目数据上的草案质量分布（KA-2 的证据缺口）。
- 预算额度的业务锚点（每日/每项目多少次调用算合理）——需用户输入或从 outboundLog 历史用量反推。
- 新编排 UI 与已交付 Xanthil 设计语言版五视图的视觉融合范围。

## Verdict

**go**——无 kill 标准已触发。条件：KA-1、KA-2 的证据在 IMPLEMENT 前补齐（用户回访 + 半天盲评），KA-3 作为 PRD 硬约束（预算按次数/轮次/墙钟三线封顶），KA-4 在 GRILL 用关口表自证。
