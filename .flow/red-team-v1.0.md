# Red-Team: Report Studio 独立报告与汇报工具（v1.0 方案）

评审对象：`.flow/proposal.md`（Report Studio 产品方案与落地框架 v1.0）。
评审时间：2026-09-22。方法：提取承重假设 → 钢人化后攻击 → 按 影响×被证伪概率×测试成本 排序。

## Top Kill-Assumptions（按优先级排序）

### 1. 技术承重假设：开源/可用引擎能产出"中文 + 可编辑 PPTX + 达标视觉质量"的会议页面

- **Claim：** 存在一条工程路径，使标题/正文/表格原生可编辑、常用图表为可编辑对象、中文长标题不溢出，且视觉达到"专业商务"水准（§4.3、§11.5、§14 M0）。
- **Steelman：** python-pptx / pptxgenjs 等对文本、表格、形状的控制成熟；原生图表可通过 chart XML 写入；设计质量靠受控设计系统（版式、字号、留白）而非引擎本身。
- **Fails if：** 在选定的操作系统 + 演示软件组合上，任何引擎组合都无法同时做到：关键页面类型可读、主要对象可编辑、中文不溢出/不缺字、图表数值可追溯——那么产品的核心交付承诺（"基础可编辑 PPTX"）不成立，只剩截图式 PPT，方案自己已声明不接受。
- **Evidence to get this week：** M0 本身——用候选引擎手工构造 §11.2 的 8 种页面类型各 1 页（含中文长标题、表格、柱线图、脚注），在真实 Office/WPS 中打开逐项核对可编辑性与排版。
- **Kill criterion：** 若经 1–2 轮引擎验证仍无组合能通过"标题/正文/表格可编辑 + 无格式阻断"，则砍掉或根本收窄 PPTX 承诺（降级为 PDF 定稿 + PPTX 大纲），重新立项。
- **Cheapest test：** 见上，M0 样例页（数天工作量，方案已正确地把它排在第一位）。

### 2. 价值承重假设：在隐私约束下，模型产出的大纲/初稿达到"可用起点"，而不是"精致的手动排版器"

- **Claim：** 材料理解 → 大纲 → 页面主旨这条链路，在允许的模型（外部经授权 / 本地）下，质量足以让用户从初稿继续编辑而不是从头重写（§2.3、§5.2）。
- **Steelman：** 结构化任务（按受众组织页序、绑定已有结论与数字）比开放式生成可控得多；确定性代码负责数字与引用，模型只做理解与文字表达（§8.2），这是正确的分工。
- **Fails if：** 企业材料不允许外发 + 本地模型弱，初稿质量低于用户手写大纲，产品退化为"带校验的排版工具"——有价值但撑不起"减少从材料到定稿的时间"这一核心主张。
- **Evidence to get this week：** 取 2–3 份真实形态的零售复盘材料（脱敏即可），跑"模型出大纲 → 人工评大纲可用性"，对比人工从零组织大纲的耗时。
- **Kill criterion：** 连续 3 次真实材料试验中，模型初稿返工量 ≥ 人工组织，且用户明确表示不会从初稿开始 → 价值假设削弱，需收窄定位（如"半自动：用户给大纲，工具出页面"）。
- **Cheapest test：** 一次性脚本 + 人工评估，1–2 天。

### 3. 需求承重假设：目标用户要"受控、可信、先大纲后生成"，而不是"一键出稿再改"

- **Claim：** 专业场景下用户接受门禁式流程（确认大纲 → 生成 → 局部编辑 → 检查），并因此减少返工（§5、§15"重复使用"）。
- **Steelman：** 一键生成工具（Gamma、Kimi PPT、WPS AI 等）的通病恰是数字漂移与整稿重生成；对要上经营会的人，"经得起追问"比"快"更硬。
- **Fails if：** 用户在首次真实任务中跳过大纲确认、直接要一键结果，且对质量下降的归因落在工具头上；或第二份真实任务不再使用（§15 重复使用指标直接证伪）。
- **Evidence to get this week：** 找 1–2 位真实目标用户，用"手工模拟的工具产出"（人肉按 M1 流程做一份汇报）观察其反应与二次使用意愿。
- **Kill criterion：** 首批真实用户 0/2 在第二次任务中继续使用 → 独立产品价值不成立，重新评估（含是否提前走 JuanerAI 集成路线）。
- **Cheapest test：** 人肉concierge 测试，半天/人。

### 4. 范围承重假设：F01–F12 的 MVP 范围能在导出核心被证明之前不被自身吃掉

- **Claim：** 开发顺序坚持"手工结构化内容 → 高质量导出 → 再接解析与编排 → 最后编辑与门禁"（§14.1），MVP 不失焦。
- **Steelman：** 方案已明确写出反模式（"不要先做复杂 Agent 编排和大量模板"），里程碑是门禁制而非时间制。
- **Fails if：** 实际开发先铺项目管理、材料解析等"好做"的面，导出质量最后才验证——那正是方案自己列的头号风险（§17"格式承诺过大"）。
- **Kill criterion：** 若 M0 门禁未通过就开始铺 M1 的广度功能，视为流程违规，必须回退。
- **Cheapest test：** 本次 dev-flow 的拆解顺序本身就是测试——任务清单第一片必须打穿"ReportSpec → 渲染 → PPTX/PDF"。

### 5. 采用环境假设：默认设计系统能落地，企业模板引力不吞噬首期价值

- **Claim：** 首期一套打磨的简洁商务主题即可支撑真实使用（§4.2），不需要任意模板导入。
- **Steelman：** 复盘/专题汇报多数没有强制品牌模板；且方案把"任意企业模板导入"明确划出首期。
- **Fails if：** 首批用户所在组织强制统一模板，所有产出必须回贴到公司模板，节省的时间被回贴吃掉。
- **Evidence to get this week：** 问首批种子用户一个问题："你们的经营会汇报有强制模板吗？"
- **Kill criterion：** 多数种子用户回答"有且强制" → 首期验证场景换到无强制模板的场景，或把"映射到用户模板"提前。
- **Cheapest test：** 一个问题。

## What's Well-Reasoned（明确站得住的部分）

- **诚实边界意识是这份方案最强的部分**：三条不可混淆界线（§3.3）、验证状态分层（绑定来源 ≠ 真实，§10.1）、"本地优先"不虚假宣传为全程不外传（§12.1）、效果指标不预设数字（§2.3、§15）——这些直接消解了 AI 报告工具最常见的信任崩塌路径。
- **工程分工正确**：模型管理解与表达、确定性代码管计算/校验/文件生成（§8.2），数字一致性由代码复算（§10.2），这是对"模型口算"这一普遍故障源的结构性防御。
- **M0 先行的排序本身就是本红队要出的最便宜测试**，方案与红队结论互相印证。
- **模块化单体 + 本地文件存储**的技术克制（§8.1、§8.2）与"独立运行"目标匹配，没有为未来集成预建重设施。
- **风险表（§17）与红队发现高度重叠**，说明方案作者对自身弱点有清醒认知，非乐观文档。

## What I Couldn't Assess

- **没有具名种子用户/试点安排**：方案定义了样板场景（零售经营复盘），但未给出谁能提供真实材料与二次使用观察。假设 2、3 的测试依赖此事。
- **"专业美观"无锚定**：无设计样张、无对标截图，M0 的视觉验收目前只有文字描述，实际标准将在 M0 中由样例第一次具体化。
- **团队与工期约束未知**：MVP 范围（F01–F12）对单人 vs 小团队差异巨大；本 flow 按方案给定的顺序执行，但预算（60 轮）内大概率完成 M0 + M1 骨架而非全部 F01–F12，需在拆解时明确本 flow 的交付边界。
- **附件两张概念图**：方案已声明其为示意（名称/时间以本文为准），未作为规范输入；如其中含 UI 布局意图，仅作参考不作约束。

## 结论

**Verdict: GO。** 五个承重假设中没有任何一个的 kill criterion 已被满足；其中最危险且最便宜的测试（M0 样例验证）恰好是方案自己排定的第一步。红队的主要增量是：①把"模型初稿可用性"列为与导出引擎并列的一等验证项；②要求种子用户与模板引力两个外部事实在本周内用最低成本确认；③警示本 flow 拆解必须保持"导出核心先行"的切片纪律。
