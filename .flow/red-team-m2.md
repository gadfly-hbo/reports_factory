# Red-Team: Report Studio M2 范围（稳定性与真实使用）

评审对象：`.flow/proposal.md`（M2 固化稿，上游 v1.0 §14）。评审时间：2026-09-22。

## Top Kill-Assumptions（按 影响×被证伪概率×测试成本 排序）

### 1. 回归样例的 golden 比对可以稳定成立——若按"字节哈希"设计则必然翻车

- **Claim：** 回归样例集能对导出产物做可重复的比对基线（M2 交付"回归样例"）。
- **Steelman：** 产物由确定性渲染器生成，同一 spec 理论上产出同一文件。
- **Fails if：** golden 采用 PPTX/PDF 字节哈希——pptxgenjs 写入时间戳、PDF CreationDate、zip 元数据都会随次变化；v1.0 §10.4 明确**不承诺跨渲染版本字节一致**。字节 golden 会在第一次重跑时随机失败，回归集立刻失去信用。
- **Evidence to get this week：** 连续两次生成同一 spec 的产物，对比字节哈希（预计不等）与抽取文本（预计相等）。
- **Kill criterion：** 若归一化文本 + 对象形状断言（页数/原生对象/关键文本）也无法稳定（如 ECharts SVG 内嵌随机 id），则 golden 退化为"关键文本集合比对"，仍可用。
- **Cheapest test：** 一个脚本，两轮生成 + diff。

### 2. "导出隐私检查"给出的是真实保障还是虚假安心

- **Claim：** 对外导出前的隐私检查（隐藏页/备注/附录/元数据/图表底层数据）+ 图表降级选择能满足 §12.2/§13.3。
- **Steelman：** 检查项可枚举、可测试；图表降级（原生 chart→图片）技术上直接；元数据可清理；这是确定性代码，不是模型判断。
- **Fails if：** 检查清单存在盲区（如 PPTX notes 页、PDF 附件、图表缓存数据残留）而 UI 又宣称"已检查可外发"——比不检查更糟：**虚假的可信承诺**恰是 v1.0 全篇反对的东西（§3.3、§17"误把来源绑定当真相"同构风险）。
- **Kill criterion：** 若无法对"已声明检查的每一项"给出自动化测试证明，则该功能只能以"检查清单 + 明示未覆盖项"形式交付，不得宣称全面保障。
- **Cheapest test：** 构造一个"带毒"样例（备注含敏感词、图表含底层数据、元数据含作者名），断言检查器逐项命中且降级导出后毒项消失。

### 3. "纯重构行为不变"有 68 项测试兜底

- **Claim：** 标准轴重构（死代码删除、布局收口、去重、类型化）在现有测试安全网下零行为变化。
- **Steelman：** 测试打的是外部行为 seam（API/E2E/渲染契约），正是重构要保住的东西；冒烟脚本补 UI 层。
- **Fails if：** 重构触碰测试未覆盖的路径（如 workspace 布局的边界分支）——概率中低，且失败表现为测试红而非静默漂移。
- **Kill criterion：** 重构后任何测试/冒烟变红且无法以"测试写错了"解释 → 停止该步重构，回退。
- **Cheapest test：** 重构即测试（每步跑 verify）。

### 4. M2 阶段门"多次实际使用可重复完成"能在此轮达成——不能

- **Claim/事实核查：** 该门需要真实用户重复使用（§15 重复使用指标），本 flow 无法采样。
- **结论：** 本轮交付的是 M2 的**工程基座**（版本比较、隐私检查、回归集、重构），M2 门本身需用户侧真实使用后判定。**PRD 必须明示这一点，不得在 DONE 总结里宣称 M2 门通过。**
- **Cheapest test：** 无——这是记录边界，不是可测假设。

### 5. 版本比较值得做结构化 diff 而非整稿快照并排

- **Claim：** §5.3"显示修改前后差异"需要页/块级结构化 diff。
- **Steelman：** 修订存完整 spec 快照，diff 是确定性纯函数，可精确测试（M1 编辑稳定性测试已提供"范围外不变"的已知答案）。
- **Fails if：** UI 层做成精细双栏渲染，工作量吞掉预算且非 M2 核心（返工/稳定性的关键在"知道改了什么"，不在排版精美）。
- **Kill criterion：** diff 视图超出"清单式呈现 + 按页分组"的成本预期 → 砍 UI 精细度保 API。
- **Cheapest test：** API diff 对 M1 的编辑用例（只改第3页标题）应恰好报一处变更。

## What's Well-Reasoned

- 范围切分忠实于 v1.0 §14 的 M2 定义，未夹带 M3/M4 私货；真实用户反馈明确划出工程边界（只交模板与指标口径）。
- 隐私检查放在版本比较之前的位置正确：§13.3 质量门槛的后半句是未兑现的承诺，属真实缺口而非锦上添花。
- XLSX 沿用 A1"预算不足首先砍"的处理，不升级为承诺。
- 继承约束清单显式锁死可信规则不回退——防止重构窗口成为"顺手改行为"的口子。

## What I Couldn't Assess

- PPTX 元数据的实际清理深度（pptxgenjs 对 docProps 的控制面）——需实现时验证，必要时 jszip 后处理。
- 外部分享在当前产品中尚无真实使用场景（无分享通道），隐私检查先行属于"能力就绪"而非"使用验证"。

## 结论

**Verdict: GO。** 无 kill criterion 已满足。两条硬性设计约束来自本次评审：①回归 golden 必须基于归一化文本 + 对象形状，禁止字节哈希；②隐私检查必须"逐项可测 + 明示未覆盖项"，不得宣称全面保障；③DONE 总结不得宣称 M2 阶段门通过（需真实使用数据）。
